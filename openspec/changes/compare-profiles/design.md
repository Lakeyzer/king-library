## Context

Every stat the compare page needs already exists per-user and is fetched client-side against a `userId` param: `useBooks().fetchProfileBookStats(userId)` (overall/Bachman/Dark Tower/collection progress) and `useAdaptations().fetchViewingProgress(userId)` (adaptations watched progress) - see profile-showcase. The two new things are (1) a route that takes two identities instead of one, and (2) a diff between two users' read/owned/watched sets, which nothing today computes.

Profile routes in this app are deliberately six independent leaf pages (own + by-username, × three tabs) rather than a nested-route parent, to avoid a header-stacking bug documented in `useProfile.ts`. The compare route is a new, seventh kind of leaf: by-username only (there's no "your own compare" - comparing needs two identities), reached from `/profile/[username]/compare`.

## Goals / Non-Goals

**Goals:**
- Reuse the existing per-user stat fetchers unchanged; add only what's genuinely new (the diff queries).
- Keep the compare page's privacy/sign-in gating consistent with the other profile routes' established pattern (redirect to sign-in, 404 on unknown username, "this profile is private" state), rather than inventing new gating language.
- Make the responsive row→column behavior a single reusable pattern applied identically to every comparison block, rather than one-off per block.

**Non-Goals:**
- No comparison history, sharing, or "invite to compare" flow - this is a same-session, on-demand view.
- No comparison of Bookshelf editions, currently-reading state, or reading timeline - the proposal scopes this to progress categories plus read/owned/watched diffs.
- No new database views or migrations - everything is computed client-side from existing tables, same as the showcase.

## Decisions

**Diffing happens client-side, reusing the `userBooksByWorkId`/full-list shape already used for stats.**
Alternative considered: a SQL function or view that takes two user ids and returns the diff server-side. Rejected for the same reason `fetchProfileBookStats` and `fetchViewingProgress` are client-side joins today (see their code comments) - the data volume (one bibliography, a few hundred works/adaptations) makes a round trip plus an array diff cheap, and it avoids a second code path (SQL vs. TS) for what is otherwise the same "read/owned/watched" boolean logic already expressed in TypeScript.

New composable functions, added alongside the existing per-user fetchers rather than replacing them:
- `useBooks().fetchReadDiff(userIdA, userIdB)` → `{ onlyA: WorkHighlight[], onlyB: WorkHighlight[] }`, built from two `user_books` queries (`read = true` for each id) plus one `king_works` lookup to hydrate titles/covers/slugs for the ids that appear in exactly one side's read set.
- `useBooks().fetchOwnedDiff(userIdA, userIdB)` → same shape and same `king_works` lookup as `fetchReadDiff`, filtered on `owned = true` instead of `read = true`. Added later, alongside `ProfileCompareDiffCard`, as a second book-side diff block ("Books Owned") mirroring "Books Read" exactly - same reasoning as the read diff, since ownership is just a different boolean on the same `user_books` row.
- `useAdaptations().fetchWatchedDiff(userIdA, userIdB)` → `{ onlyA: AdaptationHighlight[], onlyB: AdaptationHighlight[] }`, mirrored from `user_adaptations` (`watched = true`).

Both return a fixed `{ onlyA, onlyB }` shape (not keyed by user id) - the compare page always knows which side is "the signed-in visitor" and which is "the other user" positionally, matching how `fetchProfileBookStats`/`fetchViewingProgress` are already called twice (once per user id) rather than once with both ids.

**The compare page is its own leaf page, not folded into `ProfileRouteChrome`.**
`RouteChrome` renders one profile's header + tabs; a comparison has two profiles and no tabs. Reusing it would mean threading a second profile through a component built around one. Instead `app/pages/profile/[username]/compare.vue` fetches both profiles itself (the signed-in user's own via `useProfile().profile` - already loaded by the onboarding middleware, same as `pages/profile/index.vue` - and the target's via `fetchProfileByUsername`), resolves the self-compare and privacy cases per the profile-compare spec, and renders a small comparison-specific header (both avatars/usernames, no tabs) followed by the stacked comparison blocks.

**One shared block component for the row↔column responsive pattern - now scoped to the three diff-list pairs only.**
`ProfileCompareRow` takes a left slot/props and a right slot/props and renders `flex flex-col sm:flex-row` (stacked below `sm`, side-by-side at `sm` and up) - the same breakpoint already used elsewhere in this codebase for two-column responsive layouts (e.g. `Showcase.vue`'s `grid-cols-1 sm:grid-cols-3`/`sm:grid-cols-2`). Each diff-list pair is one instance (left = "what you've read/owned/watched that they haven't", right = the reverse). This keeps "always one row at a time, never a wide multi-column table" as a property of the shared component rather than something each diff block has to reimplement.

**Every named block on the page - `Total Activity`, `Reading Progress`, and each of the three diff rows - gets an `<h2>` at the same size, sitting outside that block's card/grid/pair of cards.** Revised three times. First pass: no headings at all, category identity lived only in each diff card's repeated title (e.g. "Books Read" on both the left and right card). Second pass: `Total Activity` got a smaller `<h3>` *inside* its own card while `Reading Progress` got a larger `<h2>` above the three diff rows - inconsistent both in size and in nesting (some headings inside their block's container, some outside). Current: every top-level named block - `Total Activity`, `Reading Progress`, and, one level down, each of `ProfileCompareRow`'s three instances ("Books Read" / "Books Owned" / "Adaptations Watched") - renders the same heading markup: an `<h2>` at `text-base font-semibold` with a `size-5` icon, placed outside that block's card/grid/card-pair rather than nested inside it. There's no visual size distinction between the two nesting levels (page block vs. row within the diff-rows group) - all five headings on the page read as one consistent size, and the grouping is conveyed by proximity/order alone, not by a heading-size hierarchy. `ProfileCompareRow`'s `title`/`icon` props - added optional in an earlier revision - carry this heading now; the row itself is what states the category, not a separate group header above all three rows.

**`Total Activity` and `Reading Progress` each wrap their heading and their content in one `flex flex-col gap-3` container, rather than leaving both as bare siblings in the page's outer `gap-8` stack.** `ProfileCompareRow` already keeps its own title snug against its two cards via its own internal `gap-3`; `Total Activity`'s `<h2>` and `Reading Progress`'s `<h2>` were initially left as plain top-level children of `compare.vue`'s outer `flex flex-col gap-8` wrapper, which put the full section-to-section `gap-8` between each heading and the content directly under it - visibly looser than the `gap-3` under every `ProfileCompareRow` title, for no reason other than which container happened to own the spacing. Wrapping each in its own `gap-3` block makes heading-to-content spacing consistent across all five headings, while `gap-8` continues to separate one whole block (heading + content) from the next. With the row carrying the category identity, each `ProfileCompareDiffCard`'s own title shrinks to just `"By {username}"` (own on the left, target on the right) via `NumberMotif` since it's now dynamic text, and its description drops the now-redundant leading username: `"{N} read books {other username} hasn't."` / `"{N} owned books {other username} doesn't."` / `"{N} watched adaptations {other username} hasn't."` - the verb alone (read/owned/watched) is enough to tell the three rows apart once the row header already states the category.

**Each diff-list side is a bounded card (`ProfileCompareDiffCard`), not an unbounded list.**
A read/owned/watched diff list has no natural size cap - a prolific reader's "books you've read that they haven't" side could run to dozens of rows, which would blow out the page's vertical rhythm next to the fixed-height progress cards above it. `ProfileCompareDiffCard` wraps a title (now `"By {username}"`, see above), a muted one-line description giving the actual count so the number is visible without scrolling, and a slot for the existing `ProfileCompareWorkList`/`ProfileCompareAdaptationList` in a fixed-height (`h-70`, ~5 rows at that list's row height) `overflow-y-auto` box - a 6th row peeking in at the bottom is the affordance that there's more to scroll, rather than a hard cutoff or a "show more" control. The height is fixed rather than capped (`max-h-*`) specifically so both sides of a `ProfileCompareRow` end up the same height regardless of how many items either list has - a short list and a long list sitting side by side otherwise made the pair look mismatched, since nothing else in the card forces the two to match. Each `ProfileCompareRow` instance renders one `ProfileCompareDiffCard` per side instead of the list component directly. "Books Owned" reuses `ProfileCompareWorkList` unchanged (it's still a list of `WorkHighlight`s, just sourced from `fetchOwnedDiff` instead of `fetchReadDiff`) - no new list component needed, only a new `ProfileCompareRow` instance alongside the read and watched ones.

**A `UProgressGroup` "Total Activity" bar sits above the category grid, showing each user's share of the two users' combined activity - not another two-bar comparison card.**
Every other chart on this page compares each user against a fixed denominator (their own total bibliography/adaptations count), so the bar is only ever as full as that user's own progress. This bar answers a different question - "of the two of you, who's done more, and by how much" - so it needs a genuinely different shape: `UProgressGroup` (Nuxt UI's only "segments that add up to a whole" primitive, distinct from the single-series `UProgress` used everywhere else) with two items, `{ value: ownTotalActivity, color: 'primary' }` and `{ value: targetTotalActivity, color: 'warning' }`, and `max` set to the sum of the two values rather than a fixed total - that's what keeps the bar always exactly full, split proportionally between the two users, instead of leaving unfilled track the way every category card's bars do. `ownTotalActivity`/`targetTotalActivity` (in `compare.vue`) are each a single number combining up to three sources per user: books read (`stats.overall.count`), books owned (`stats.collection.count`), and adaptations watched (`viewing.count`) - the three "count" metrics already fetched for the category grid, summed rather than fetched again.

**Which of the three sources feed the total is user-selectable, via a `USelectMenu` (`multiple`) on the same line as the `Total Activity` heading, justified to the end.** All three categories (`ACTIVITY_CATEGORIES`: Books Read / Books Collected / Adaptations Watched) are selected by default, matching the original fixed sum. `selectedActivityCategories` (a `ref<ActivityCategory[]>`) drives both `ownTotalActivity` and `targetTotalActivity` computeds - each now only adds a source's count if its category is present in the selection - so unchecking, say, "Adaptations Watched" narrows the bar to a pure books comparison without navigating away from the page. No option to select zero categories is blocked at the UI level; an empty selection just means both totals compute to `0`, which `UProgressGroup` already handles the same way `ownTotalActivity + targetTotalActivity === 0` does elsewhere (falls back to its own default `max`, bar reads empty) - not worth a special case for what's a deliberately-reachable, harmless edge state.

**Labels and counts are hand-built rows below the bar, not `UProgressGroup`'s own item list.** `UProgressGroup`'s built-in list (shown when items carry a `label`) renders both items stacked vertically underneath the bar - fine for an arbitrary-length list of segments, but this is always exactly two, and the readable framing for two is "each person's end of the bar," not a stacked list. So the `items` passed to `UProgressGroup` carry only `value`/`color` (no `label`, so its own list never renders), and two plain `flex justify-between` rows are built underneath it instead: a label row (a small `bg-primary`/`bg-warning` dot plus username via `NumberMotif`, own on the left, target on the right) directly under the bar, then a count row below that with the same raw combined counts on the same left/right sides - same "actual numbers over percentages" preference used throughout this page, just laid out to match the two ends of a single bar rather than a list.

**Progress categories render as a stacked horizontal-bar card per category, arranged in a responsive grid - not the row/column pattern.**
Revised four times after initial implementation. First pass: one `ProfileCompareRow` per category with two separate `ProfileProgressBar`s side by side. Second pass: a hand-built vertical two-bar chart (two bars per card on a shared baseline, filling from the bottom) since Nuxt UI ships no grouped-chart component. Third pass: the vertical bars read fine as a chart but were harder to scan for "how close are these two" than a plain progress-bar comparison, so `ProfileCompareProgressCard` stacked one `UProgress` row per user instead, with a label line (username, uppercase, muted) carrying that user's percentage right-aligned on the same line, then a bold raw `count / total` line below it, then the bar. Fourth pass (current): the count/total and the percentage read as two disconnected numbers on separate lines, when they're really one figure described two ways - so the label line now holds only the username, and the percentage moved down onto the same line as `count / total`, right-aligned against it and bottom-`items-end`-aligned (not `items-baseline`) since the two texts are different sizes and a shared bottom edge reads cleaner than a shared baseline at this size difference. Per the `dataviz` skill's procedure - color assigned by job (identity, not magnitude), fixed and never cycled, a legend wherever it applies to more than one chart, no color-only distinction:
- Colors are fixed per **user role**, not per category: `primary` (signed-in visitor) / `warning` (other user), the same two on every one of the five cards, rather than the category-identity colors the single-profile showcase uses (`primary`/`neutral`/`secondary`/`success`/`info`) - those encoded "which category" for a single bar; this encodes "which person" across two bars, a different job.
- Each bar carries its own username label directly above it (not a shared legend above the grid) - identity reads locally per bar rather than requiring a round trip to a legend above five repeated charts.
- The count/total figure is the raw **count / total**, not just a percentage - per the "actual numbers" request, a percentage told a visitor "how far along" but not "by how much," which is what a head-to-head comparison is actually for. The percentage is still shown, on the same line, so neither figure is lost.
- A `UProgress` `title` attribute (`"{username}: {count} / {total}"`) carries the same numbers on hover.
- Each card's title row also carries a difference badge (`UBadge`, `variant="subtle"`) justified to the far end of the title line - `success` + up-arrow + `+N` when the signed-in visitor leads, `error` + down-arrow + `-N` when behind, no badge on a tie. This is the fastest-scanning way to answer "who's ahead here" per category without reading both bars' numbers and subtracting them mentally.

The five cards sit in a `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-4` - 3 columns at `lg`, 2 at `md`, 1 below that - since a compact chart (unlike a full diff list) reads fine several-to-a-row and grouping them lets a visitor compare categories against each other, not just the two users within one category. Overall Bibliography carries `md:col-span-2` (the widest category, and the one a visitor scans first) so it spans two grid tracks from `md` up instead of sitting at the same width as the other four. This only applies to the five progress-category cards; the two diff-list pairs (read-books, watched-adaptations) keep the original one-at-a-time row/column layout, since a list of titles needs the full row width a grid cell wouldn't give it.

**Compare control placement in the header.**
`Header.vue`'s existing non-owner branch (`v-else`) renders only the follow/unfollow button. It becomes two controls side by side - Compare (a plain link, always available the moment the follow control would render, since the button is only shown for a public profile per profile-showcase's new requirement - no separate loading state needed) and the existing follow/unfollow button - rather than a new conditional branch, since both are shown under the same signed-in-non-owner condition. The compare button additionally needs the current user's own username to build its `/profile/[username]/compare` target's *implicit* other half is the route's own `[username]` param - i.e. the link only needs the viewed profile's username, nothing new to plumb into `Header.vue` beyond what it already has.

## Risks / Trade-offs

- **N+1-ish fan-out for large bibliographies**: the diff fetchers each pull two full boolean sets plus one full `king_works`/`adaptations` table, same volume `fetchWorkHighlights`/`fetchProfileBookStats` already pull today. Not a new scaling concern at current data size (~100s of rows).
- **Self-compare and private-target checks both happen client-side after a fetch**: mirrors how `pages/profile/[username]/index.vue` already 404s after `fetchProfileByUsername` resolves `null`. Consistent with existing pattern, not a new risk class.
- **Two diff queries plus two stats fetches per page load** (one pair per user) is more round trips than a single-profile showcase. Acceptable since `Promise.all` already parallelizes the equivalent fan-out on the showcase page.
