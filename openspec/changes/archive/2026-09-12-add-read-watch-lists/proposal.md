## Why

There's currently no page where a signed-in user can see the full list of King works they've read or the full list of adaptations they want to watch — that data only surfaces piecemeal (progress bars, the Bookshelf, per-item toggles). Separately, a visitor looking at someone else's public profile has no way to spot a good, low-risk gift idea: a book that person has already read (so it's a known interest) but doesn't own a copy of.

## What Changes

- Reorganize the profile page into three tabs sharing a persistent header (avatar, username, tagline, share/follow control): **Reader Checklist** (the existing dashboard — timeline, reading progress, currently reading, bookshelf, recommendations), **Read List**, and **Watch List**. Each tab is a real route, not client-only tab state, so it's linkable/shareable on its own.
- Add a **Read List** tab: lists a user's King works marked `want_to_read` (the to-read queue, not reading history) — mirrors Watch List's to-do semantics rather than "books already finished." Reachable both as the signed-in user's own shortcut (`/profile/read-list`) and by username (`/profile/[username]/read-list`) for viewing anyone's public list, mirroring the existing `/profile` vs `/profile/[username]` split.
- Add a **Watch List** tab: lists a user's adaptations marked `want_to_watch` (the to-watch queue, not the watched history). Same own-shortcut-plus-by-username reachability (`/profile/watch-list` and `/profile/[username]/watch-list`).
- Both list tabs reuse the existing `BibliographyBrowsePage`/`BibliographyListItem` browsing layout (search, type filter, cover thumbnails) already used by `/works`, `/adaptations`, and `/short-works`, rather than a bespoke layout, so a personal list looks and behaves consistently with the rest of the app's browsing pages — minus the sort control, which doesn't make sense for a short personal queue and is hidden on these two tabs specifically. `BibliographyBrowsePage` gains an optional empty-state (icon/title/description), since its existing behavior (render nothing when `items` is empty) never came up on the full-bibliography pages it already powers but does here.
- Add links to both new tabs in the header's account dropdown menu, and restructure that menu into grouped sections separated by dividers (Nuxt UI `UDropdownMenu`'s array-of-arrays form) instead of one flat list.
- Add a new **gift idea recommendation** to the Reader Checklist tab: when a signed-in visitor views someone *else's* public profile, show a recommendation for one King work that's on that person's read list but not on their shelf (`want_to_read = true AND owned = false`), with the meta text "It's on their read list, but not their shelf." Shown only to non-owner visitors, never to the profile owner viewing their own showcase.

## Capabilities

### New Capabilities
- `read-list`: A tab showing a user's want-to-read King works, reachable as the signed-in user's own shortcut and by username for any public profile.
- `watch-list`: A tab showing a user's want-to-watch adaptations, reachable as the signed-in user's own shortcut and by username for any public profile.

### Modified Capabilities
- `app-shell`: The account menu gains links to the new Read List and Watch List tabs, and its items are grouped into sections separated by dividers instead of one flat list.
- `profile-showcase`: The profile page is now organized into three tabs (Reader Checklist, Read List, Watch List) behind a persistent header, rather than one page showing everything; a non-owner visitor also now sees a gift-idea recommendation on the Reader Checklist tab for a King work on the profile owner's read list but not their shelf.

## Impact

- **New/restructured pages**: six independent leaf pages — `app/pages/profile/index.vue`, `read-list.vue`, `watch-list.vue` (own-shortcut) and `app/pages/profile/[username]/index.vue`, `read-list.vue`, `watch-list.vue` (by-username) — deliberately *not* a Nuxt nested-route parent+`<NuxtPage />` structure: that was tried first, but a `profile.vue` parent for the own routes ended up also parenting `profile/[username].vue` (since it lives inside the same `profile/` directory), rendering both the visitor's own header and the viewed profile's header stacked together. Each tab fetches only its own data, so visiting Read List no longer pulls Reader Checklist's timeline/stats/bookshelf and vice versa.
- **`app/composables/useProfile.ts`**: new `ViewedProfileContext`/`viewedProfileKey`/`useViewedProfile()`, plus a synchronous `provideViewedProfile(profile)` — each leaf page resolves its own `Profile` (own: already-loaded, no fetch; by-username: `await useAsyncData(...)` + 404, directly in the page's own script) and then calls `provideViewedProfile()` right after, which `provide()`s the derived context for the tab-content component it renders to read via `inject()` (`useViewedProfile()`). Deliberately not an async composable that does its own fetch-then-provide internally — that was tried first and broke `provide()` for the by-username routes, since `<script setup>`'s async-context restoration only covers awaits written directly in the page's own script, not a separate composable's internal ones (see nuxt-conventions).
- **`app/components/profile/Header.vue`** (new): avatar/username/tagline/share-or-follow control, extracted out of `Showcase.vue`.
- **`app/components/profile/Tabs.vue`** (new): the three tab links, built from a `basePath` prop (`/profile` or `/profile/[username]`). Uses `UNavigationMenu` with `highlight`, not `UTabs` — `UTabs` is local-state (`v-model`) only and has no `to`/link concept, so it can't drive real routes the way `UNavigationMenu` (already used for the primary header nav) does.
- **`app/components/profile/RouteChrome.vue`** (new): the plain, non-async, prop-driven wrapper every leaf page renders directly — `Header` + (private notice, or `Tabs` + the page's slotted-in tab content). Not a route-level parent, precisely to avoid the nested-routing bug above.
- **`app/components/profile/Showcase.vue`**: now Reader Checklist tab content only (rendered via the new `ReaderChecklistTab.vue` wrapper) — header/share/follow moved to `Header.vue`; gift-idea recommendation added to the non-owner path (existing recommendations stay `isOwner`-gated and untouched).
- **`app/components/profile/ReaderChecklistTab.vue`**, **`ReadListTab.vue`**, **`WatchListTab.vue`** (new): the three tabs' actual content, each shared between the own-shortcut and by-username routes through `useViewedProfile()` rather than being duplicated per route.
- **`app/components/BibliographyBrowsePage.vue`**: new optional `emptyIcon`/`emptyTitle`/`emptyDescription` props and a two-tier empty state (genuinely-empty vs filtered-to-nothing, mirroring `ProfileBookshelf`'s existing split), plus an optional `showSort` prop (default `true`) hiding the sort field/direction controls while the list still sorts internally for a stable order — all additive and backward compatible, since `/works`/`/adaptations`/`/short-works` omit the new props and keep their current behavior.
- **`app/components/core/AppHeader.vue`**: `accountMenuItems` restructured from a flat `DropdownMenuItem[]` into grouped `DropdownMenuItem[][]`, with two new entries (`/profile/read-list`, `/profile/watch-list`) added.
- **`app/composables/useBooks.ts`**: `fetchReadList` (returning a `ReadListEntry` with `type` added, for `BibliographyBrowsePage`'s type filter), and `fetchGiftIdeaRecommendation` (`want_to_read = true AND owned = false`, not gated to `isOwner`, so it works for a non-owner viewer per RLS).
- **`app/composables/useAdaptations.ts`**: `fetchWatchList` (returning a `WatchListEntry` with `type` and `releaseYear` added, same reason).
- **`app/middleware/onboarding.global.ts`**: sign-in gate list updated to the new own-shortcut paths (`/profile/read-list`, `/profile/watch-list`) in place of the earlier standalone `/read-list`, `/watch-list`.
- No schema changes — all underlying fields (`want_to_read`, `owned`, `want_to_watch`) already exist on `user_books` / `user_adaptations`.
