## Context

See proposal.md for motivation. Relevant current state:

- `king_works` and `adaptations` have no `slug` column; the only stable identifier today is the UUID `id`.
- Canonical bibliography/adaptation data is seed-file-driven (`supabase/seed/*.json` + loader scripts under `supabase/seed/`) — see `supabase-conventions`. Rows are never written by the client.
- `/works` and `/adaptations` render via `BibliographyBrowsePage` → `BibliographyListItem`, a generic list item component (title, thumbnail, year, type, an `#actions` slot). Neither component currently produces a link.
- `BookReadingActions` (`app/components/book/ReadingActions.vue`) renders one compact `UFieldGroup` (a primary `UButton` plus a `UDropdownMenu` for secondary actions), gated on `useSupabaseUser()`.
- The app has made no external calls to Open Library or TMDb from application code yet — `open_library_work_key`/`cover_id` and `tmdb_id`/`tmdb_media_type`/`tmdb_poster_path` exist on the tables but nothing has fetched live detail from either API.
- `@nuxt/ui` v4 ships `UPage` (a `left` / default / `right` three-slot layout primitive) and `UPageAside`, used together elsewhere in the Nuxt UI ecosystem for a main-content-plus-sidebar page shape.

## Goals / Non-Goals

**Goals:**
- Stable, human-readable URLs for works and adaptations, backed by an indexable DB column.
- A reusable "detail with sidebar" page shell, distinct from the plain `default` layout.
- First live integrations with Open Library and TMDb, done safely (no exposed TMDb key) and degrading gracefully when data is missing or a fetch fails.
- An expanded reading-status control layout, without duplicating reading-status business logic.

**Non-Goals:**
- Short story detail pages or short-story routing (explicitly deferred by the user).
- Editing, caching layers, or rate-limit handling for Open Library/TMDb beyond a single per-page-load fetch — acceptable for current traffic; revisit if it becomes a problem.
- SEO/meta-tag work beyond what falls out naturally from page titles.
- Any change to reading-status's underlying data model or write behavior — only a new presentation of existing actions.

## Decisions

### 1. Slug: stored column, generated at seed time

Add `slug text not null unique` to both `king_works` and `adaptations`. Slugs are generated once, from title, by the seed loader (lowercase, spaces/punctuation to hyphens, diacritics stripped, e.g. "'Salem's Lot" → `salems-lot`), and written into the seed JSON files (or generated by the loader script and persisted) so they're stable and reviewable like the rest of the curated bibliography — consistent with "canonical bibliography curated manually" in CLAUDE.md. A migration adds the column and backfills existing rows from their current titles before the `not null unique` constraint is applied.

Detail pages fetch by slug directly (`.eq("slug", slug).single()`), which needs the column to be a real, indexed table value rather than computed per-request — this was confirmed with the user over computing a slug on the fly from title (rejected: no efficient indexed lookup, and a later title edit would silently change every existing link).

If two titles would ever collide (none do today across either canonical list), the loader appends `-2`, `-3`, etc.; this is a loader-script concern, not a spec-level behavior.

### 2. Detail routes fetch-by-slug and 404 on miss

`app/pages/works/[slug].vue` and `app/pages/adaptations/[slug].vue`, each using `useAsyncData` against a new composable function (`fetchKingWorkBySlug(slug)` / `fetchAdaptationBySlug(slug)`, mirroring the existing `fetchKingWorks`/`fetchAdaptations` shape). A miss (`PGRST116`/no row) triggers `createError({ statusCode: 404, statusMessage: 'Not found' })` inside the page, which Nuxt renders as its standard error page — no custom not-found UI needed for this change.

`fetchAdaptationBySlug` also resolves the adaptation's linked works/short stories in the same call (join through `adaptation_works`/`adaptation_short_stories`), since the detail page always needs them. `fetchKingWorkBySlug` stays narrow (own-table fields only); the adaptations-based-on-this-work and short-stories-in-this-collection lookups are separate composable calls (`useAdaptations`/`useShortStories`) run alongside it on the page, since those already have (or will gain) their own list-fetch shapes and are needed by other pages too.

### 3. New `detail` layout built on `UPage` + `UPageAside`

`app/layouts/detail.vue` reuses `default`'s header/footer, wrapping the page's `<slot />` in `UPage` with the page's own `#right` content passed through a named slot the layout exposes (Nuxt layouts can declare their own slots the same way `default` exposes the implicit default slot). Concretely:

```
CoreAppHeader
UMain > UContainer > UPage
  center: <slot />              (page's main content)
  #right: <UPageAside><slot name="aside" /></UPageAside>
CoreAppFooter
```

`UPage`'s own responsive behavior (stacking `left`/center/`right` on narrow viewports) covers the "reachable, stacked" mobile requirement from the app-shell delta spec — no bespoke breakpoint handling needed.

Alternative considered: a single layout with an optional aside slot, toggled by a prop/`definePageMeta` flag, instead of a second named layout. Rejected because Nuxt layouts are already the app's mechanism for shell variants (per the existing app-shell spec), and a boolean flag on `default` would make `default` implicitly two shapes instead of the spec's "exactly one" becoming "exactly two, each named."

### 4. External API calls: Open Library direct from client, TMDb via a server route

Open Library's API is public and keyless, so work-detail enrichment calls it directly from the client inside the page's data fetching (a small `useOpenLibraryWork(workKey)`-style composable, matching the `openlibrary-integration` skill once that's written).

TMDb requires an API key. To avoid shipping it to the browser, add `server/api/tmdb/[mediaType]/[id].get.ts` that reads the key from `runtimeConfig` (server-only) and proxies the single "get details" call the adaptation page needs; the adaptation detail page calls this server route instead of TMDb directly. This is the first server-proxied external call in the app; `server/api/` already exists for `account.delete.ts` so the pattern isn't new to the project, just to this data path.

Both enrichment fetches are best-effort: a failure (network error, 404 from the upstream API, missing key/id) is caught and simply omits the enrichment section, per the work-details/adaptation-details specs — it never blocks or errors the rest of the page.

### 5. `BookReadingActions` gains a `mode` prop

Add `mode?: "compact" | "expanded"` (default `"compact"`, so every existing call site is unaffected). `compact` keeps today's `UFieldGroup` (primary button + dropdown) exactly as-is. `expanded` renders the same per-state action set as today's `dropdownItems` computed, but as individual `UButton`s with no dropdown — same handlers, same modals (`BookStartReadingModal`/`BookFinishReadingModal`/`BookMarkReadModal`), just a different template branch keyed on `mode`. No change to `useBooks` or any reading-status data logic — this is presentation-only, matching the reading-status delta spec's "same actions, same effects" requirement.

### 6. Detail-page navigation and sidebar connections

- `BibliographyListItem` gains an optional `to` prop (a route location); when set, the title (and thumbnail) render inside a `NuxtLink`, while the `#actions` slot content stays outside the link so action buttons don't trigger navigation. `BibliographyBrowsePage` gains a `detailPathPrefix` prop (`"/works"` / `"/adaptations"`) and builds `to` as `` `${detailPathPrefix}/${item.slug}` ``, requiring `slug` on its generic item constraint alongside the existing `id`/`title`/`type`.
- A new small component family, `components/detail/ConnectionList.vue` (`<DetailConnectionList>`), renders the sidebar's titled list of related items (adaptations on a work page, source works on an adaptation page, short stories in either): a heading plus a compact vertical list of thumbnail+title rows, each optionally wrapped in a `NuxtLink` (omitted for short story rows, which have no detail page yet). This is intentionally not `BibliographyListItem` reused as-is — the sidebar rows have no year/type/actions row, just a compact link — but it's built from the same Nuxt UI primitives (`UPageAside` content, `NuxtImg`, `NuxtLink`) rather than hand-rolled markup.

## Risks / Trade-offs

- **TMDb/Open Library latency or downtime** on page load → mitigated by the best-effort/non-blocking enrichment decision above; the page is fully usable from local data alone.
- **No response caching** for either external API means repeat visits to the same detail page re-fetch every time → acceptable for now given expected traffic; revisit with a cache layer if TMDb rate limits become a problem.
- **Seed-time slug generation is a one-way door**: once slugs are seeded and linked to from outside the app, changing the slugging algorithm later is a breaking change to existing URLs → mitigated by keeping the algorithm simple and documenting it in the loader script; not a concern for this change's scope.
- **`UPage`'s built-in responsive stacking** is relied on as-is rather than custom-built → if its default breakpoint/behavior doesn't match expectations once built, adjusting is a small follow-up, not a redesign.

## Migration Plan

1. Add the `slug` migration (column + backfill + `not null unique` constraint) and update seed JSON/loader scripts to include slugs for every existing and future row. Push to hosted Supabase before merge, per the project's release process.
2. Ship the composable/route/layout/component changes together; nothing here is independently deployable in a way that benefits from splitting further.
3. No rollback complexity beyond the standard migration revert — the new column is additive and nothing existing depends on its absence.
