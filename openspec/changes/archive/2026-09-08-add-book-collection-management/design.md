## Context

`user_book_editions` is already fully specified in `supabase-conventions` (schema, RLS, and the "adding an edition is a two-write operation owned by `useBookshelf()`" rule) but no migration for it exists yet — this change is its first implementation. `EditionList.vue` already fetches and paginates Open Library editions in two layouts: a horizontal infinite-scroll scroller (`orientation="auto"`, sm+) with a search box, and a vertical paginated list (always rendered as the small-screen fallback in `auto`, or exclusively in `orientation="vertical"`) with no search box today. `ReadingActions.vue` (`BookReadingActions`) already has a compact dropdown-menu mode and an expanded separate-buttons mode, both gated on `user`. See proposal.md for why this is being built now.

One documented rule this change deliberately supersedes: `supabase-conventions` currently says removing a work's last edition row does not auto-flip `owned` back to `false`. That was written before any UI existed to add/remove editions at all. Per the proposal, this UI is now the only way `owned` gets set, so it also owns clearing it — the skill doc needs a follow-up edit once this ships (tracked in tasks.md).

## Goals / Non-Goals

**Goals:**
- One shared "is this edition already in my collection" toggle control, usable from three call sites (editions picker modal, on-page edition list, Bookshelf tile) without duplicating add/remove logic.
- Vertical edition list gains search parity with the horizontal one, without changing the horizontal one's behavior.
- Bookshelf laid out as a genuine masonry wall, per the explicit request, reading left-to-right the way a masonry wall is expected to (see "Bookshelf grid: round-robin columns" for how three different mechanisms were tried before landing on this one).

**Non-Goals:**
- Editing or annotating an edition once added (condition notes, purchase price, etc.) — out of scope, not requested.
- Manually entering an edition that isn't in Open Library's results — the Open Library link covers that gap by sending the user to add it there instead.
- Reordering or curating Bookshelf tile order beyond a fixed, stable sort.

## Decisions

### Ownership-clearing lives in the composable, not a DB trigger
`useBookshelf().removeEdition()` deletes the edition row, then counts the user's remaining edition rows for that `king_work_id`; if zero, it upserts `user_books.owned = false` in a second call. This mirrors the existing add-side two-write pattern (`useBookshelf().addEdition()` inserts the edition row, then upserts `owned = true`) rather than introducing a delete trigger on `user_book_editions`.

Alternative considered: a DB trigger (`after delete on user_book_editions`, clear `owned` if no rows remain) for the same reason the app already uses triggers for `user_books`' own invariants (`clear_wishlist_on_owned`, etc.). Rejected because this isn't a table-level invariant the way those are — a work can legitimately be `owned` with zero edition rows (the edition-less case this same change explicitly supports on the Bookshelf), so "0 editions" must not unconditionally imply "not owned" at the schema level. The cascade only makes sense as "the thing that just removed the last edition also clears the flag it's responsible for," which is exactly what the composable call site already knows and the two-write pattern already establishes for `addEdition`.

### Vertical-mode search reuses the existing `loadAll()` pattern
`EditionList.vue` already has a `loadAll()` used when horizontal-mode search needs the full result set client-side (Open Library's API has no publisher/year filter param). Vertical mode gains the same search input, wired to the same `loadAll()`-on-nonempty-query behavior; once loaded, pagination for a search paginates over the filtered in-memory array instead of issuing further offset/limit fetches. An empty query reverts to the existing page-by-page server fetch (`loadPage`), so the common no-search case doesn't change its network behavior.

### One toggle component, three call sites
A single edition-row add/remove control (add icon button when not in the collection, a filled/"remove" state when it is) is built once and used by: the editions picker's vertical list, the on-page `WorkEditionList`, and Bookshelf tiles. All three read the same `useBookshelf()` state (a `Set` of added edition keys per work, exposed similarly to `useBooks()`'s existing `userBooksByWorkId` pattern) so adding from one place reflects immediately in the others without a refetch.

### Editions picker is `EditionList` forced to vertical, inside a modal
No separate editions-fetching logic — the picker is `WorkEditionList :work-key="..." orientation="vertical"` inside a `UModal`, with the add/remove control rendered per row and the Open Library link in the modal footer.

### Vertical edition rows: leaderboard-style list, not `BibliographyListItem` cards
The vertical layout (used by both the modal, exclusively, and the small-screen fallback of `orientation="auto"`) originally reused `BibliographyListItem` — the same per-item `bg-elevated`-card-with-large-thumbnail component the works/short-stories/adaptations browsing pages use. In the editions picker that read as too large/heavy for a plain pick-a-copy list. Replaced with a bespoke, more compact row (`ul.divide-y.divide-accented`, matching `WorkLeaderboard`'s row styling) rather than reusing `BibliographyListItem`, since that component is shared with the browsing pages and changing its default look was out of scope - the goal was specifically the editions list, not those pages too.

Thumbnail size within that same row layout is **not** uniform across the two contexts that share it, though — the picker modal (`orientation="vertical"`) keeps the small `xs` size (compactness matters there, scanning many candidate editions), while the on-page small-screen fallback (`orientation="auto"`) uses `sm` (`ImageThumbnail`'s default), matching `DetailConnectionList`'s own mobile fallback so the editions section doesn't look oddly cramped next to the rest of the detail page's connection lists at the same width. `rowThumbnailSize`/`rowCoverSize` computeds branch on `props.orientation` for this; both the real rows and their loading skeleton read from them.

### Full-size cover preview: one shared modal, both orientations
A click on any edition thumbnail with a cover (horizontal card or vertical row) opens the same `UModal` showing that cover at the `L` size, reusing the already-established `getOpenLibraryCoverUrl` helper - no new cover-fetching logic, just a bigger size variant of the id already in hand. An edition with no cover renders the thumbnail as a non-interactive button (`cursor-default`, click is a no-op) rather than omitting the wrapper entirely, keeping row layout identical whether or not a given edition has art.

### Bookshelf grid: round-robin columns
Three mechanisms were tried, in order:

1. **Native `grid-template-rows: masonry`** (Tailwind arbitrary-value classes). Dropped after manual testing: outside Firefox, browsers fall back to plain row-tracked CSS Grid, which doesn't pack shorter/taller tiles at all — every item in a row stretches to the row's tallest item (`align-items: stretch`, CSS Grid's default).
2. **`UPageColumns`** (`@nuxt/ui`), a CSS multi-column layout (`columns-N`). Real, universally-supported CSS, and genuinely packs tiles by height — but its packing algorithm balances columns by *total content height*, filling each column with as many tiles from the source order as fit its share of that total, rather than placing each tile into whichever column is currently shortest. For a modest tile count that reads as column-major and lopsided (e.g. columns 1-2 getting one tall tile each while column 3 gets two shorter ones to match) rather than filling left-to-right the way a masonry wall is expected to — confirmed against a real Bookshelf and rejected for that reason.
3. **Round-robin columns** (current): tile 1 to column 1, tile 2 to column 2, ..., wrapping back to column 1 once every column has one — a small hand-rolled layout (plain `flex` columns, no Nuxt UI component or CSS masonry technique fits this), computed client-side from a `columnCount` ref that's recalculated from `window.innerWidth` on mount and on resize (2 at the smallest breakpoint, 3 at `sm`, 5 at `lg` — matching the same Tailwind breakpoints used elsewhere, just evaluated in JS since the column-to-item assignment itself has to change per breakpoint, not just the CSS). Gives the expected left-to-right reading order deterministically, at the cost of balancing by tile *count* rather than real height — an explicitly accepted trade-off, not a bug (see Risks below). SSR renders the 2-column default since there's no viewport to read yet; the client corrects it after mount, same as any other JS-computed responsive layout without CSS container queries.

### Bookshelf tiles render at each cover's natural aspect ratio
Tiles do **not** reuse `ImageThumbnail` (used everywhere else covers appear in the app) because its `size="full"` forces a fixed `aspect-[2/3]` crop via `object-cover` — every tile would render the same height, which defeats masonry regardless of which mechanism produces it (nothing to pack; a uniform layout looks the same either way). The Bookshelf tile instead renders the image at its natural size (`w-full`, no forced aspect ratio, no `object-cover`), so cover images of different real proportions actually produce different tile heights to pack. The no-cover/loading-error state falls back to a fixed `aspect-[2/3]` placeholder box (icon + the work's title, truncated) since there's no real image to size against in that case.

### Open Library returns a 1x1 pixel image, not a 404, for a cover-less id
Confirmed by fetching `covers.openlibrary.org/b/olid/{id}-M.jpg` directly for a real edition with no cover on file: `200 OK`, a 1x1 pixel GIF. `<NuxtImg>`'s `@error` never fires for that (it loaded successfully), so a naive error-only fallback silently renders a stretched, empty-looking box — which is what happened. Fixed by also checking `naturalWidth`/`naturalHeight` on `@load` and treating anything smaller than 4px as equivalent to a load error, falling back to the same icon-and-title placeholder.

### Edition tiles fall back to the work's cover
An edition can have no cover art on file even when the work it belongs to does (confirmed against real data: an owned edition with a 1x1-pixel cover, for a work that has a real cover on Open Library). An edition tile's cover-resolution order is therefore three-deep, not two: its own edition cover first; if that's missing or fails (per the 1x1-pixel check above), the work's live-fetched cover next (the same fallback a work-only tile already uses); only if both are unavailable does it fall back to the icon-and-title placeholder. `BookshelfEditionItem` carries `openLibraryWorkKey` (added alongside `publishDate`, both sourced from the same `king_works` join `fetchBookshelf()` already performs) so an edition tile has something to fall back to without an extra query.

### Tile count = total tiles rendered
Per the confirmed scope, the Bookshelf heading count is the number of tiles in the full collection (edition rows + edition-less owned works), computed client-side from the same data used to render the grid — not a separate query, and not affected by the search filter below (same convention as `WorkEditionList`'s "Editions (12)" heading, which also always reflects the unfiltered total).

### Bookshelf search and sort are client-side over already-fetched data
`fetchBookshelf()` already returns the profile owner's entire collection in one call (no pagination) - a search field (matching the King work title) and a sort control (title or release year, either direction, defaulting to release year ascending) both filter/sort that same in-memory array reactively, no new query. Sorting happens before the round-robin column split, so column assignment always reflects the current sort/filter rather than the original fetch order. Follows the same search+sort control pattern already used on `BibliographyBrowsePage` (search input, a field `USelect`, a direction-toggle `UButton`) for visual/interaction consistency, rather than inventing a new one.

### Open Library "add a missing edition" link target
`https://openlibrary.org/books/add?work=/works/{open_library_work_key}` — deep-links straight into Open Library's add-edition form pre-scoped to the work, rather than its plain editions listing.

### Edition cover ids need normalizing to a bare OLID
`user_book_editions.edition_id` is stored verbatim from Open Library's editions.json `entries[].key` field, which — like every Open Library resource `key` — is a full path (e.g. `/books/OL7353617M`), not a bare id. `getEditionCoverUrl()` strips everything up to the last `/` before building the `covers.openlibrary.org/b/olid/...` URL, since that endpoint wants the bare OLID. This is a no-op if a bare id is ever passed instead, so it's safe regardless of what ends up stored. Found and fixed after Bookshelf tiles shipped with broken edition covers (malformed olid URLs 404 silently, which `ImageThumbnail` shows as its placeholder icon rather than an error).

### Bookshelf remove control: sibling of the tile's link, not nested inside it
Each tile's cover is wrapped in a `NuxtLink` to the work's page. The remove button (`UButton`, a `<button>`) can't validly nest inside that `<a>` per HTML semantics, so it's a sibling positioned absolutely over the tile inside a shared `relative` wrapper `div`, rather than living inside the link and needing `@click.stop.prevent` to suppress navigation.

Removal always goes through a confirmation modal (`ProfileBookshelfRemoveModal`, following the same `UModal` body/footer pattern as the other book-action modals) before calling `useBookshelf().removeEdition()` or `useBooks().setOwned(workId, false)` (branching on `item.kind`) — a deliberate step given this is a destructive action with no separate undo, unlike the plain toggle used on the work detail page (where re-adding the same edition is one click away and there's no confirmation there either, but that surface is about building the collection, not casually clearing it from a dense grid).

### Removal updates a local copy of the Bookshelf items, not the fetch result
`fetchBookshelf()` is a one-time snapshot fetched via `useAsyncData` on the profile page, not state that reacts to `useBookshelf()`/`useBooks()` writes the way `userBooksByWorkId`/`userEditionsByWorkId` do. `Bookshelf.vue` keeps a local `ref` copy of the `items` prop (resynced via a `watch` when the prop itself changes, e.g. navigating to a different profile) and splices a tile out of that local copy when its `removed` event bubbles up, rather than re-fetching the whole collection or leaving a just-deleted tile visible until the next page load.

### Add to Shelf's label reflects ownership, matching the rest of the component
`ReadingActions.vue`'s other controls all flip their label with state (`readlistLabel`, `readLabel`, `startFinishLabel`) rather than staying static — Add to Shelf originally didn't follow that pattern (a static "Add to Shelf" regardless of `isOwned`), which read as broken once a user actually owned the work being viewed. Fixed with a `shelfLabel` computed (`"On Shelf"` when `isOwned`, `"Add to Shelf"` otherwise) used everywhere the control's label appears (the compact dropdown item and both expanded-mode buttons), for the same reason those other three already do it: the control stays the single entry point into the editions picker regardless of state (there's no separate "manage" control), so the label is what tells the user which state they're in.

### Owner-count stats reuse `work_stats.owner_count` and extend the existing `work_stats`/homepage queries
`work_stats.owner_count` already existed (defined before this change, per `supabase-conventions`) and was already being fetched into `WorkStats` on the work detail page, just never rendered — showing it needed a template change, not a new query. The homepage total (`useHomepage()`'s `booksOwnedCount`) is the sum of that same `owner_count` column across all works, added as a second `reduce()` over the `work_stats` rows `fetchHomepageMeta()` already selects (one extra column, `owner_count`, on the existing `work_stats` query - no new round trip), mirroring exactly how `booksReadCount` already sums `read_count` from the same result set.

### Owned-unread recommendation: new type, no shared "because" field
`fetchUnreadRecommendation()` (existing) picks an unread book because its adaptation was watched, and its `BookRecommendation` type carries a `becauseTitle` for that reason. The new `fetchOwnedUnreadRecommendation()` has no such per-item reason - it's always the same static fact ("it's on your shelf") - so it returns a separate `OwnedUnreadRecommendation` type without a `becauseTitle` field, rather than reusing `BookRecommendation` with an empty/unused field. Query shape mirrors `fetchUnreadRecommendation`'s "fetch candidates, `Math.random()` pick one" pattern, but is simpler: a single `user_books` query filtered to `owned = true, read = false` (joined to `king_works`), no adaptation-watch join needed. Powers a new display component, `WorkOwnedRecommendation`, alongside the existing `WorkRecommendation`/`AdaptationRecommendation` on all three surfaces (homepage, works browsing sidebar, profile showcase - owner-gated like the other two personalized recommendations already are there).

## Risks / Trade-offs

- **Round-robin columns balance by tile count, not real height** → A column can end up visually taller than its neighbors if it happens to receive several tall covers in a row (unlikely at typical cover-image proportions, but possible). Accepted over `UPageColumns`' height-balanced-but-column-major alternative because it reliably gives the expected left-to-right reading order, which is what was actually being asked for; true shortest-column-next packing would need real per-tile height measurement (ResizeObserver/image `load` per tile) and was judged not worth the added complexity for this trade-off.
- **Column count is computed client-side from `window.innerWidth`, not derived from CSS** → Server-rendered and initial-hydration markup always shows 2 columns (the smallest-breakpoint default) regardless of the visiting device, correcting to the real count in an `onMounted` resize check. A brief 2-column flash on a first paint at a wider viewport is possible before that correction runs. Accepted as the standard trade-off for any JS-computed (rather than pure-CSS) responsive layout; revisit only if it proves visually distracting in practice.
- **Two sequential writes for add/remove aren't atomic** (edition write then `user_books` upsert) → Same trade-off already accepted for the existing add-edition rule in `supabase-conventions`; a failure between the two calls leaves `owned` stale until the next add/remove reconciles it. Acceptable at this app's scale/consequence level (a personal collection tracker, not a financial ledger); revisit only if it causes real user-visible drift.
- **Superseding the documented "last edition removal doesn't un-own" rule** → `supabase-conventions` needs a follow-up edit (tasks.md) so the schema doc doesn't contradict the shipped behavior.

## Migration Plan

1. New migration: `create_user_book_editions_table` — table + four RLS policies, exactly as already specified in `supabase-conventions` (`user_book_editions readable by owner or if profile public` / `writable by owner only` / `updatable by owner only` / `deletable by owner only`). No new triggers.
2. Apply and verify locally (`supabase migration up`) before any hosted push, per `supabase-conventions`' local-development workflow.
3. No backfill needed — new, empty table.
