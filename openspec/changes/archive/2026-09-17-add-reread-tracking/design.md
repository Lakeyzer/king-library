## Context

`user_books` currently holds exactly one reading cycle per `(user_id, king_work_id)`: `read`, `started_on`, `finished_on`, `read_year`. The `supabase-conventions` skill already flags this as a known, deliberately accepted limitation: rereading overwrites these columns rather than preserving history, and names the fix as "a new table (e.g. `read_events`), one row per read cycle, layered on top" rather than a change to the existing columns.

The reading timeline (`app/components/profile/ReadingTimeline.vue`, fed by `useBooks().fetchReadingTimeline()`) currently queries `user_books` directly, so it renders one entry per work. `EditReadDatesModal.vue` calls `markRead()` to adjust an existing work's dates in place. Stats (`work_stats` view, showcase progress bars, category-completion views) all key off the `user_books.read` boolean and are unaffected by anything below as long as that boolean's semantics don't change.

See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Preserve every distinct read as its own record (date, note, format, rating), without touching the "read at least once" semantics `user_books.read` and its dependent stats/progress views already provide.
- Let a user log a reread without unmarking the work first.
- Extend the existing read-completing modals with note/format/rating instead of introducing a parallel UI flow.

**Non-Goals:**
- No change to how "read" is counted in `work_stats`, showcase progress bars, or category completion — they keep reading `user_books.read` as-is.
- No editing or deleting of an arbitrary past logged read beyond what the existing date-adjustment entry point already supports (see "Editing a logged read" below). Building a full read-history management UI (edit/delete any past entry's note/format/rating) is out of scope for this change.
- No aggregate "times reread" stat or "average personal rating" display — the proposal only asks that reads not be deduplicated on the timeline, not that new aggregate stats be built.
- No change to short-story reread tracking (`user_short_story_reads`) — this change is scoped to `user_books`/King works, consistent with how the existing schema already keeps short-story reads as a simpler row-existence table.

## Decisions

### A new `user_book_reads` table, additive to `user_books`
One row per logged read: `id`, `user_id`, `king_work_id`, `read_on` (date, nullable — mirrors `user_books.finished_on`'s optionality), `read_year` (int, nullable, same fallback role as `user_books.read_year`), `note` (text, max 200 chars, nullable), `format` (text enum: `physical` / `audiobook` / `ebook`, nullable), `rating` (int 1–5, nullable). No unique constraint on `(user_id, king_work_id)` — rereads are the point.

Alternative considered: repurpose `user_books` itself into a one-row-per-read model and drop the single-cycle columns. Rejected — it would break the "one row per `(user_id, king_work_id)`" invariant that RLS policies, the ownership/wishlist triggers, and `work_stats` all currently depend on, for no benefit: stats only ever need "read at least once," which the existing boolean already answers.

Alternative considered: store note/format/rating as JSON on a `user_books.read_history` column. Rejected — same reasoning `supabase-conventions` already gives against cramming history into a single-value field: it can't be queried, ordered, or constrained (e.g. rating range, note length) at the database level.

### `user_books.read`/`started_on`/`finished_on`/`read_year` stay as the "current status" summary
Every read-completing action (finish, mark-read-directly, read-again) does two writes, same two-write pattern already used elsewhere in this schema (e.g. adding an edition also upserts `user_books.owned`): upsert `user_books` (`read = true`, and `started_on`/`finished_on`/`read_year` updated to reflect this latest read, same as today) and insert one `user_book_reads` row. This keeps `work_stats`, progress bars, and category completion working unmodified, and keeps `user_books` a cheap "is this read, and when most recently" check without a join.

### Read-again reuses the mark-read-directly prompt
No new modal component. The existing optional-dates-and-now-note/format/rating prompt is shown for: finishing a currently-reading work (end date only, prefilled), marking read directly (all fields optional), and reading again (all fields optional, identical shape to mark-read-directly). Read-again is available whenever `user_books.read = true`; it does not require or touch `currently_reading`/`want_to_read`.

### Unmarking read deletes all logged reads, after confirmation (revised)
**Revised from the original decision below** (kept for history): unmark no longer preserves logged read history. On confirmation, it deletes every `user_book_reads` row for that `(user_id, king_work_id)` and clears `user_books.started_on`/`finished_on`/`read_year` in addition to flipping `read` to `false` — a full reset rather than a status flip, matching the product decision that "unmark" means "this was a mistake, undo all of it," not "hide the read count but keep history around." A confirmation step (a plain modal, not the Bookshelf-removal feature's Dark-Tower "Say true?"/"Say thankya" phrasing — that phrasing is specific to that feature, not a house style to reuse elsewhere) is required first since this is now a destructive, unrecoverable action.

~~Original decision: Unmark only flips `user_books.read` to `false` (existing behavior, dates untouched). Logged reads are treated as permanent history, independent of the work's current status flag.~~ Superseded by product feedback during implementation.

### Starting a new read on an already-read work (coexistence of `read` and `currently_reading`)
A work that's already marked read can be started again without unmarking first — `currently_reading` and `read` can both be `true` at once while that new session is in progress. This requires a fix to the `clear_read_states_on_progress()` trigger (see "Trigger fix" below), plus `finishReading`/`markRead`/`readAgain` explicitly setting `currently_reading = false` in their own writes rather than relying solely on the trigger.

**Why the trigger alone can't handle this**: the existing trigger's rule was "whenever `read` ends up `true`, force `currently_reading` and `want_to_read` false." That rule can't stay as-is once starting a read no longer implies "not already read" — `startReading()`'s write doesn't touch `read` at all (its `user_books` upsert omits that column, relying on Postgres's on-conflict semantics to leave `read` at its current value), so when the work is already read, `NEW.read` is `true` purely because it was already `true`, not because this write is trying to complete anything. The old trigger can't distinguish "`read` is `true` because this write just completed a read" from "`read` is `true` because it already was, and this write is only starting a new session" — both present the same `NEW.read = true` to the trigger. Fix: only auto-clear `currently_reading`/`want_to_read` when `read` is *transitioning* to `true` (`old.read is distinct from true`, same pattern already used by `cascade_short_story_reads_on_collection_read`) — this stops the trigger from fighting `startReading()`. That alone reopens a gap for the opposite case (finishing a *second* read on a work that was already read before this session started: `old.read` is already `true`, so the transition-only trigger no longer fires) — closed by having `finishReading`/`markRead`/`readAgain` explicitly include `currently_reading: false` in their own writes instead of depending on the trigger for it. Verified end-to-end against local Supabase (see tasks.md).

### `user_books.format` captures the current reading session's format
A work being read hasn't produced a `user_book_reads` row yet (that only happens once the read completes), so the Currently Reading card — which needs to show a format icon *while a work is still in progress* — has nothing in `user_book_reads` to read from. A new nullable `format` column on `user_books` fills that gap: `startReading()` writes it (explicitly nulling it out when not supplied, same reasoning as `markRead`'s dates — otherwise a stale format from an earlier session would resurface on conflict), and `fetchCurrentlyReading()` selects it. This is a distinct concept from `user_book_reads.format` (the format of a *completed* read): the two are never read from each other, and `finishReading`/`markRead`/`readAgain` don't touch this column at all — its only consumer is the Currently Reading card, gated on `currently_reading = true`, so a stale value from a finished session simply stops being displayed (nothing reads it) rather than needing to be cleared.

Alternative considered: derive the currently-reading card's format from the work's *most recent* `user_book_reads` row instead of adding a column. Rejected — that row reflects the *previous, already-completed* read, not the one in progress; showing it while a new session is underway (which may end up in a different format) would be actively misleading, not just imprecise.

### Reading Timeline page reuses the existing timeline component via an `orientation` prop
Rather than a second component or a rename into a component-family folder, `ReadingTimeline.vue` gains an `orientation?: 'horizontal' | 'vertical'` prop (default `'horizontal'`, so the existing showcase widget is unaffected). Horizontal keeps the drag-scroller/chevron-button chrome; vertical renders the same `UTimeline` with `orientation="vertical"` and no scroller chrome. The dedicated page pair (`profile/timeline.vue`, `profile/[username]/timeline.vue`) follows the exact same own-shortcut/by-username/privacy pattern as `read-list`/`watch-list` (see nuxt-conventions and the read-list capability) — a new `ProfileTimelineTab.vue` tab-content component fetches via the same `fetchReadingTimeline()` call (same `useAsyncData` key as the showcase widget, so the two share cache) and renders `ReadingTimeline` with `orientation="vertical"`. The showcase's Reading Journey heading gets an end-justified link to this page, built from `isOwner`/`profile.username` the same way `basePath` is already computed for `ProfileRouteChrome`.

### The two orientations show different levels of detail, and lay out differently (revised)
**Revised from the original decision above** (kept for history): the two modes diverged further than originally planned, based on product feedback during implementation:
- **Detail level**: the horizontal showcase widget shows only each entry's work and date (matching profile-showcase's requirement) — note/format/rating render only in vertical mode, on the dedicated page. The `#description` slot template is simply omitted from the horizontal `<UTimeline>`; `timelineItems` still carries the fields either way; the horizontal branch just never displays them.
- **Layout**: vertical mode is a centered zigzag (entries alternating left/right of a vertical line), not UTimeline's default single-column vertical list.

### Vertical zigzag layout follows Nuxt UI's documented recipe, not a hand-rolled one (revised)
**Revised from the layout approach above**: the first attempt (absolutely-positioning `container` at the item's midpoint, capping `wrapper` to half-width) didn't actually alternate anything when checked against the running app — `container`'s absolute positioning conflicted with `item`'s own layout in a way that never got verified visually (this whole change's UI work was implemented and typechecked without the dev server, per CLAUDE.md's testing workflow — this is exactly the kind of bug that gap allows through). Replaced with [Nuxt UI's own documented alternating-layout recipe](https://ui.nuxt.com/docs/components/timeline#with-alternating-layout), adapted to this app's indicator size:

- Even items get `flex-row-reverse` (swaps icon/text order) plus `-translate-x-[calc(100%-Wi)]` (Wi = the indicator's rendered width), which cancels the reversal's offset so the icon lands back in the *same* column odd items' icons already occupy — the two don't alternate icon position, they share one column.
- The whole `<UTimeline>` gets `translate-x-[calc(50%-Wi/2)]`, nudging that shared icon column from the left edge to the true center — without this, "same column" would mean "flush left," not centered.
- `indicator: 'size-12'` (3rem) matches the horizontal branch's own indicator size explicitly, rather than letting the smaller size the `size="sm"` prop alone would produce (Avatar's `sm` = `size-7` = 1.75rem) apply — cover thumbnails should render the same size in both places. `Wi = 3rem` (not the docs' own `2rem`, tuned to *their* demo's default indicator) drives the constants: `calc(100%-3rem)` and `calc(50%-1.5rem)`.
- `wrapper` additionally needs `max-w-[calc(50%-2.25rem)]` — the reverse/translate trick only relocates the *indicator*; it does nothing to stop each side's text from growing most of the way across the item's full width, which without a cap visually overlaps the opposite side's content well before reaching the centerline. `2.25rem` = half the indicator's width (1.5rem, clearing the centered indicator) plus `item`'s own `gap-3` (0.75rem, clearing the flex gap between indicator and text) — the same two clearances the horizontal branch's `pl-6` (also 1.5rem) exists for, just expressed as a max-width cap rather than a padding offset since the horizontal branch pulls its indicator out of flow entirely via `absolute` (losing the natural flex `gap` in the process, which is what `pl-6` compensates for) while this vertical layout keeps its indicator in-flow and gets that gap for free.
- Still gated behind `sm:` — below it, none of these classes apply and the timeline falls back to the plain single-column vertical layout, avoiding two cramped reversed columns on a phone screen.
- Getting either the size or the max-width constant wrong wouldn't error — it would just misalign the columns or let text overlap, exactly the kind of silent-looking-wrong-not-broken issue that needs the running app to actually catch, which is why this remains flagged for manual visual verification rather than checked off on typecheck alone.
- `wrapper` also gets an ungated `pb-10`, replacing the `sm`-size default's `pb-6`, for more breathing room between consecutive nodes along the line — this one isn't zigzag-specific (applies at every width, including the single-column mobile fallback), it's just more legible spacing for the list itself.

### `text-align` doesn't reposition block-level flex rows - `#description`'s format/rating row needs its own `justify-end`
`wrapper`'s `sm:even:text-end` sets `text-align`, which only repositions *inline* content - it's why the note paragraph's text follows the alternation for free (a `<p>`'s text is inline content of a block box) but the format/rating row (a `flex` row, itself block-level) didn't: `text-align` has no effect on where a block-level flex container sits or how it justifies its own children. Fixed by adding `sm:group-even:justify-end` directly on that row. `group-even` reaches up to the nearest `.group` ancestor - which is `item` itself, since Nuxt UI's own base theme already puts `group` there for its `group-data-[state=...]` indicator styling - so this reuses the *exact* same even/odd determination the item-level `sm:even:flex-row-reverse` override already relies on, rather than introducing a second, potentially-inconsistent way of asking "is this entry on the reversed side."

### Timeline queries `user_book_reads` instead of `user_books`
`fetchReadingTimeline()` changes its source table; each row becomes one timeline entry (date from `read_on` falling back to `read_year`, plus note/format/rating). Ordering: most recent first, same `coalesce(...) desc nulls last` pattern the skill already documents for the current `user_books`-based query.

### Editing a logged read
The existing pencil-icon date-edit affordance on a timeline entry now edits that specific `user_book_reads` row (date, note, format, rating) rather than `user_books`. If the edited entry is the work's most-recent logged read, the corresponding `user_books.started_on`/`finished_on`/`read_year` summary is updated to match, same two-write pattern as above; editing an older, non-most-recent entry updates only that `user_book_reads` row.

### RLS
`user_book_reads` gets the same four-policy owner-or-public-profile pattern already used for `user_books`, `user_book_editions`, `user_adaptations`, and `user_short_story_reads` — no new pattern needed.

### Expanded-mode controls: slots are repurposed per state, not accumulated (revised)
Read Again and start-from-read (both added earlier in this change) pushed the read state's expanded-mode button count to 5 (a disabled-but-still-rendered readlist toggle, start/finish, Mark as Unread, Read Again, Shelf) — the reading-status spec's expanded-mode requirement never mandated a *fixed, ever-growing* button per action, only that whatever actions apply to the current state each get their own separately activatable control rather than being grouped behind a secondary menu (see that requirement's text) — but nothing stopped that number from growing unboundedly as actions were added over the course of this change, and it visibly did.

Fix: `ReadingActions.vue`'s expanded mode now has exactly 3 slots (plus Shelf when applicable) — leftmost, start/finish, read-related — and the **leftmost slot's meaning changes per state** instead of a new slot being added for each new action:
- neutral / want-to-read: readlist toggle (unchanged).
- currently-reading: hidden entirely (`v-if`, not `:disabled`) — nothing meaningful belongs there once reading is underway, and a rendered-but-disabled button was dead space contributing to the crowding even before this change's additions.
- read (not currently-reading): **Mark as Unread**, moved here from sharing the read-related slot with Read Again.

The read-related (3rd) slot then holds exactly one control per state — Mark as Read (neutral/want-to-read/currently-reading) or Read Again (read) — rather than two side-by-side controls for the read state. This is a pure re-layout: every action the spec's expanded-mode requirement lists as available for a given state (want-to-read, start-reading, mark-as-read, finish, unmark, read-again) is still its own directly-clickable control with the same effect — none were removed, merged into a dropdown, or hidden behind a secondary control — so no spec change was needed, only the arrangement. Start/finish (the middle slot) is untouched by any of this; it was never part of the overcrowding.

### Adding a read from search reuses `MarkReadModal` as-is, via a new `logged` emit
"Add to Timeline" is two existing pieces wired together rather than a new read-logging path: a new `BookSearchWorkModal.vue` (client-side title filter over `useKingWorks().fetchKingWorks()`'s already-active-only list, via `USelectMenu`'s built-in search) emits the selected `KingWork`, and `ProfileTimelineTab.vue` then opens the existing `BookMarkReadModal` (default `mode="mark"`) for it — the exact same prompt/fields/behavior as marking any other work read, just reached by searching instead of already being on that work's page. No new read-logging logic exists anywhere in this feature.

The one real gap: `ProfileTimelineTab.vue`'s `readingTimeline` list is a one-time `useAsyncData` snapshot, so a read logged through this flow wouldn't appear until the next full page load. `MarkReadModal` gained a `logged` emit (fired after a successful `markRead`/`readAgain` call, alongside its existing `open.value = false`) purely so this one caller can call `refresh()` on that `useAsyncData` — existing callers (`ReadingActions.vue`) don't listen for it and are unaffected, since they already react to `markRead`'s update of the shared `userBooksByWorkId` state directly.

Alternative considered: filter the search to only active-but-not-yet-read works. Rejected — searching a work the user has already read is a legitimate way to log *another* read for it (this flow has no reason to special-case that any differently than the existing per-work "Read Again" action does), and there's nothing in the request suggesting the search should be a "first read only" picker.

## Risks / Trade-offs

- **Two writes instead of one, per read-completing action** → mitigated by following the same two-write convention already established for editions/ownership; both writes are the composable's responsibility, not a trigger, consistent with existing precedent (`supabase-conventions` explicitly prefers this over a trigger here for the same reasons it gives for ownership-clearing).
- **`user_books` summary fields and `user_book_reads` can, in principle, drift** (e.g. a direct SQL edit to one but not the other) → same accepted risk profile as the existing `owned`/edition-row relationship; no stronger consistency mechanism exists elsewhere in this schema either, and a trigger was rejected above for the same reasons already documented for that case.
- **A reread logged with an earlier date than an existing entry** (backdating) is not explicitly ordered/validated against other entries for the same work → accepted; the existing single-cycle model has no such validation either, and imposing one here would be new scope beyond what's requested.
- **Unmarking read is now a permanent, unrecoverable deletion of read history** (reversed from the original "preserve everything" decision) → mitigated by requiring explicit confirmation before the delete runs, and by the confirmation copy naming what's about to be lost (note/format/rating included) rather than a generic "are you sure?".
- **The `clear_read_states_on_progress()` trigger change is a behavior change to a shared trigger**, not something scoped to this feature's new table → mitigated by verifying every existing scenario the trigger covers (want-to-read → currently-reading, currently-reading → read, neutral → read) still holds under the new transition-only condition, in addition to the new coexistence case, via direct SQL replay against local Supabase before considering the migration done.

## Migration Plan

1. Add `user_book_reads` table + RLS policies as a new, additive migration — no change to `user_books`'s existing columns or constraints.
2. Backfill: for every existing `user_books` row with `read = true`, insert one corresponding `user_book_reads` row from its current `started_on`/`finished_on`/`read_year` (with note/format/rating left null), so existing read history isn't lost and the timeline doesn't regress to empty for users who already have reads recorded.
3. Alter `clear_read_states_on_progress()` (see "Starting a new read on an already-read work" above) so starting a read on an already-read work isn't immediately reverted by the trigger.
4. Ship the composable/UI changes (dual-write, read-again action, confirm-then-delete unmark, start-reading-from-read, updated timeline query, the dedicated timeline page) in the same release as the backfilled table and trigger fix — the timeline UI depends on `user_book_reads` existing and populated, and the reread-on-an-already-read-work flow depends on the trigger fix being live first.

Rollback: `user_books` itself is untouched by step 1-2, so reverting those only needs to drop the new table. Reverting step 3 (the trigger change) requires reverting to the original unconditional clear — safe only if step 4's app code (which now also explicitly clears `currently_reading` itself) is rolled back in the same step, since the two changes depend on each other for the coexistence case to work correctly.
