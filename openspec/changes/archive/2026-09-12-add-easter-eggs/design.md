## Context

See proposal.md for motivation. Relevant current state:

- The color mode toggle and the sign-out action both live inline in `app/components/core/AppHeader.vue` (sign-out calls `supabase.auth.signOut()` directly from a dropdown item, no dedicated composable).
- `BookshelfRemoveModal.vue` is the app's only generic destructive "are you sure?"-style confirm dialog. `DeleteAccountModal.vue` is a separate, already-easter-egged dialog and is out of scope here.
- The Works, Short Stories, and Adaptations browsing pages intentionally mirror each other's structure (per each capability's stated purpose) and, in practice, all render through a shared `BibliographyBrowsePage.vue`/`BibliographyListItem.vue` pair that owns search, filtering, and list rendering.
- Work and adaptation detail pages already call `createError`/`showError` for unresolved slugs; there is no shared visual not-found page today, and no top-level `error.vue`.
- There is no existing utility for scanning/styling substrings within rendered text (no highlighting, no letter-glitching).
- `king_works`/`adaptations` seed data is the canonical bibliography (per CLAUDE.md) and is not meant to carry presentational joke data.

## Goals / Non-Goals

**Goals:**
- One small, reusable way to highlight standalone `19`/`1999` tokens, applied consistently at every place the app renders dynamic text - bibliography data (titles, dates, counts, stats, descriptions) and user-authored content alike (profile taglines, usernames, edition publishers, reading-timeline dates, progress/stat labels) - not just a curated subset of pages.
- A shared Overlook Hotel-themed not-found page that both Nuxt's default unmatched-route handling and the existing per-entity `createError`/`showError` calls resolve to.
- Every other easter egg implemented as a small, targeted change to the one existing component it belongs to.

**Non-Goals:**
- No generic reusable confirm-dialog component — only `BookshelfRemoveModal.vue`'s copy changes; `DeleteAccountModal.vue` is untouched.
- No database schema or seed data changes; Charlie the Choo-Choo's and Misery's special behaviors are keyed off their known slugs in front-end code, not new fields.
- No blanket DOM-wide text scanning (e.g. a `MutationObserver`, or a generic VNode-tree walker reaching into other components' own templates) for either the number-motif highlight or the N-glitch. Both are applied by explicitly wrapping each text expression the two Misery pages (and the number-motif's broader set of pages) already author directly in their own templates — never to `<title>`, meta tags, aria-labels, form/input values, or text generated inside separately-owned shared components (see the N-glitch decision below for what that excludes on the Misery pages specifically).
- No changes to `seo-metadata` capability behavior; the not-found page still gets its own page-specific title/description per that capability's existing rules.

## Decisions

**Number-motif highlighting is a small component applied at every dynamic-content render point across the app, not a global DOM/VNode scan.** `NumberMotif.vue` splits a text string on a digit-boundary regex equivalent to `(?<!\d)(1999|19)(?!\d)` (longer alternative first) and wraps each match in a `text-warning` span. Initial coverage (this design's first pass) was limited to bibliography-derived data - a real gap surfaced by manual testing, where a profile tagline containing "19" wasn't highlighted since profile/settings/following templates hadn't been touched. Coverage was then extended to every direct-text-interpolation render site across the app's `.vue` files: bibliography titles/dates/counts/descriptions as before, plus profile taglines and usernames (`Showcase.vue`, `following.vue`, `settings.vue`), edition publishers/years (`EditionList.vue`), reading-timeline dates (`ReadingTimeline.vue`), Bookshelf/collection counts and item titles, homepage stats tiles and catalog counts, and progress-bar counts/percent/hint text. Left unwrapped, deliberately: static configuration strings that are always the same literal value regardless of data (section headings like "Collections"/"By the Numbers", nav/button labels, Nuxt UI `label`/`title` prop values rendered inside another component's own template - the same component-encapsulation boundary documented for the N-glitch below), the live `<UInput v-model>` a visitor is actively typing into (splitting its value into spans would break editing), OAuth error text and HTTP status codes (transient system messages, not app content), and a TMDb rating (`toFixed(1)` on a 0-10 scale can never produce 19). Alternative considered: a global DOM `MutationObserver` or VNode-tree walker mounted once at the app root, so no per-component wiring is ever needed — rejected because it would splice/replace the actual text nodes or VNodes Vue's own reactivity system owns and later updates; any span it injected around a reactively-updating value (a stat count changing live, for instance) would break that binding the next time Vue tried to patch it, since Vue would be updating a node no longer in the place it expects. Explicit per-component wrapping has no such conflict, at the cost of needing to remember to wrap new render sites as they're added.

**Not-found page reuses Nuxt's built-in error-page mechanism.** A single `app/error.vue` (Nuxt's convention for both unmatched routes and thrown errors) gets the Overlook Hotel visual treatment and the "You've wandered into a room that isn't on the floor plan." copy. The existing `createError`/`showError` calls in the work/adaptation/profile detail pages continue to fire as they do today; because they already produce a 404 error, Nuxt routes them to the same `error.vue`, so no per-page change is needed beyond confirming each still triggers a real error rather than rendering an ad hoc inline message. Alternative considered: a bespoke `NotFoundState` component each detail page renders inline — rejected as duplicated effort when Nuxt's error page already centralizes this.

**Room 217 is implemented once, in the shared `BibliographyBrowsePage.vue` component the three browsing pages already render through.** (Correction from this design's original assumption that the three pages had no shared search/list component - they do: `BibliographyBrowsePage.vue` + `BibliographyListItem.vue`.) One conditional - trimmed search text `=== '217'` and zero results - shows the hidden message in place of the existing empty list, satisfying all three pages' identical requirement at once.

**Room 217 also covers the global search dialog, added separately (`add-global-search`, merged to `main` after this change was proposed and merged in here).** `useGlobalSearch.ts`'s `groups` computed already builds each category's matches before deciding what to render; when the trimmed term is exactly `217` and all three categories come back empty, it returns one label-less group holding a single disabled item with the eerie message, instead of the normal three (each-with-their-own-"No matches") groups. A label-less group is a deliberate use of `CommandPalette`'s existing behavior - `ListboxGroupLabel` only renders when a group's label is truthy, so `label: ""` cleanly suppresses the category header without needing a new prop or template change in `GlobalSearch.vue`.

**Confirm-dialog wording change is scoped to `BookshelfRemoveModal.vue` only.** It's the sole generic confirm-style dialog in the app; its "Remove" confirm button becomes "Say thankya" and its prompt copy incorporates "Say true?". `DeleteAccountModal.vue` keeps its own distinct existing quote per the earlier decision to leave it unchanged.

**Charlie the Choo-Choo and Misery special cases are slug-keyed conditionals in the existing detail page components**, not new data fields — e.g. `work.slug === 'charlie-the-choo-choo'` / `work.slug === 'misery'` (and the equivalent adaptation slug check). This keeps the canonical bibliography data free of presentational joke content.

**Charlie the Choo-Choo name loop: alternates every 6 seconds, indefinitely, with a letter-scramble transition.** A small `ScrambleText.vue` component owns the animation - it watches its `text` prop and, on change, animates from the previous value to the new one by revealing each character at a randomized offset/duration (classic staggered "decode" scramble effect, ~1s total), padding the shorter of the two names so the effect reads cleanly across their different lengths. The byline's own timer just flips between the two name strings on a `setInterval`, leaving the transition itself entirely to `ScrambleText`. The interval is cleared on component unmount to avoid a dangling loop after navigation.

**N-glitch covers every text expression the Misery pages' own templates author, at reduced opacity rather than a muted color.** `GlitchLetter.vue` (a small text-to-nodes helper splitting on `/[Nn]/`) now takes an `active` prop so call sites stay unconditional (`:active="isMisery"` renders plain text on every other work/adaptation) and wraps each match in an `opacity-40` `<span>` instead of `text-muted`. On both Misery pages it's applied to the title, byline/directed-by line, type and runtime/season text, the description/overview/notes, and the stats row labels - i.e. everything the page template itself renders as text. It deliberately stops at the boundary of separately-owned shared components (`BookReadingActions`/`AdaptationWatchActions`'s button labels, `WorkEditionList`'s edition rows, `DetailConnectionList`'s "Adaptations"/"Based on" entries, and any `UBadge` `label` prop) since reaching into those would mean threading a Misery-only concept through components every other page also reuses - not a mutation of a shared component's own behavior, which the site header and footer (also excluded, per the requirement) are further examples of. Alternative considered: a generic VNode-tree walker wrapping the whole hero slot to catch every text node regardless of which template authored it — rejected as a nontrivial, hard-to-verify piece of low-level Vue internals (vnode cloning/children-normalization) to introduce for a cosmetic effect, versus the small, explicit, easily-reviewed set of wrap sites actually chosen.

## Risks / Trade-offs

- [Risk] A digit-boundary regex could still misfire on adjacent punctuation (e.g. an apostrophe-prefixed year like `'19`) → Mitigation: match on absence of adjacent digits only, as specified; this is an intentional, narrow definition of "standalone."
- [Risk] Because coverage is a curated list of wrap sites rather than a scan, a future new page/component that renders dynamic text will silently not get the highlight until someone remembers to add `<NumberMotif>` there too → Mitigation: accepted trade-off given the reactivity-breaking alternative (see the decision above); flagged here so a future gap report (like the one that prompted this pass) isn't a surprise.
- [Risk] Wrapping every "N"/"n" across a whole page's text in individual `<span>`s could clutter the DOM or subtly affect text selection/copy behavior → Mitigation: scope to the two Misery pages only, and within them to the page's own template output (not shared components); confirm in manual testing that copy/paste still yields correct text.
- [Risk] A visitor may expect "every N on the page" to include the reading/watch-status action buttons, edition list, or connections lists → Mitigation: accepted trade-off, documented here - those live in shared components reused by every other page, so reaching into them would mean threading a Misery-only flag through unrelated, reused components.
- [Risk] The Charlie the Choo-Choo loop's `setInterval` (and any in-flight scramble animation frame) could keep running after the visitor has navigated away → Mitigation: clear the interval and cancel any pending animation frame in the components' unmount hooks.
- [Risk] Routing all "not found" results through one `error.vue` could make it harder to give an entity-specific not-found message later → Mitigation: not a concern now since no entity-specific 404 copy exists today; revisit if that's ever needed.

## Migration Plan

Front-end only; no Supabase schema or seed changes, so this ships in a normal PR merged to `main` with no pre-merge hosted-database step. No rollback complexity beyond reverting the change.
