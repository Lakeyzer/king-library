## Purpose

Serves public catalog pages from a shared cache so most visits cost no server rendering, while keeping each visitor's personal data correct and private and keeping community figures live. Nothing is ever shown in a wrong state while it loads.

## ADDED Requirements

### Requirement: Public catalog pages are served from a shared cache until the next deployment
The system SHALL serve the following pages from a shared cache:
- the homepage
- the works, adaptations, short works and works-by-others browse pages
- every work, adaptation, short work and works-by-others detail page
- the Dark Tower page

Each page SHALL be generated the first time it is requested after a deployment, and every later request SHALL be served that copy until the next deployment. A new deployment SHALL discard every cached page. The system SHALL generate the privacy policy page once per deployment and serve it unchanged.

#### Scenario: First request after a deployment
- **WHEN** a work detail page is requested for the first time since the latest deployment
- **THEN** the page is generated and stored in the shared cache

#### Scenario: Repeat request
- **WHEN** a work detail page has already been generated since the latest deployment and any visitor requests it
- **THEN** the cached page is served without generating it again

#### Scenario: Deployment discards cached pages
- **WHEN** a new version of the site is deployed
- **THEN** the next request for any cached page is served a copy generated by the new version

### Requirement: Cached page content is identical for every visitor
The system SHALL produce the cached HTML of a cached page without reading the requesting visitor's session and without fetching any data that belongs to a specific visitor. The cached HTML SHALL contain only content that is the same for every visitor, whether signed in or signed out.

#### Scenario: Signed-in visitor is the first to request a page after a deployment
- **WHEN** a signed-in visitor's request causes a cached page to be generated
- **THEN** the generated page contains none of that visitor's data (reading or watch status, wishlist, recommendations, progress, username or avatar)
- **AND** it is served unchanged to every later visitor

#### Scenario: Cached page response sets no session cookie
- **WHEN** any visitor is served a cached page
- **THEN** the response does not set or refresh an authentication cookie

### Requirement: Personal content on cached pages loads in the visitor's browser
On a cached page, the system SHALL load everything that depends on the visitor in the visitor's browser, directly from the database, after the page is displayed. This includes:
- reading, watch and short-story read status
- owned-edition and wishlist state
- personalized recommendations
- Dark Tower progress and next-book suggestions
- controls that are only offered to signed-in visitors

Once loaded, this content SHALL match what the visitor saw before this change.

#### Scenario: Signed-in visitor opens a cached work page
- **WHEN** a signed-in visitor who has read a work opens that work's cached detail page
- **THEN** the page first shows the shared content, then shows the work as read once the visitor's status has loaded

#### Scenario: Signed-in visitor sees their homepage recommendations
- **WHEN** a signed-in visitor with an eligible book recommendation opens the cached homepage
- **THEN** the recommendation appears once their data has loaded, as it did before this change

#### Scenario: Signed-out visitor
- **WHEN** a signed-out visitor opens a cached page
- **THEN** no personal content is loaded and the page shows what a signed-out visitor saw before this change

### Requirement: Community figures and date-based highlights on cached pages load in the browser
On a cached page, the system SHALL load the following in the visitor's browser, directly from the database, for every visitor whether signed in or not:
- every figure computed from users' activity: detail-page counts of readers, want-to-read, currently reading, owners, watchers and want-to-watch; the homepage stats and catalog figures; leaderboards; most-wanted, least-read and most-anticipated spotlights; Dark Tower journey stats
- every highlight that depends on the current date: Book of the week and Book birthdays

These SHALL NOT be part of the cached HTML. They SHALL reflect current data each time the page is opened, including the visitor's own actions made earlier. The current date for Book of the week and Book birthdays SHALL be the visitor's own local date.

#### Scenario: Counts are current on a cached page
- **WHEN** a work detail page was cached days ago and its read count has since changed
- **THEN** a visitor opening the page sees the current read count

#### Scenario: Visitor's own action is reflected on the next visit
- **WHEN** a visitor marks a work as read and later opens that work's cached detail page again
- **THEN** the read count includes their read

#### Scenario: Book birthdays follow the visitor's date
- **WHEN** a visitor opens the cached homepage on a date that matches an active King work's original publish month and day, in the visitor's own timezone
- **THEN** that work is shown as a book birthday, even if the cached page was generated on a different date

#### Scenario: Book of the week follows the visitor's week
- **WHEN** the cached homepage was generated in one ISO week and a visitor opens it in the next ISO week, by the visitor's own date
- **THEN** the visitor sees the Book of the week for their current ISO week

### Requirement: Content never shows a wrong state while loading
While personal data, community figures or date-based highlights for a cached page are still loading, every control and section that depends on them SHALL show a neutral loading placeholder. It SHALL NOT show a state that may be wrong, such as:
- an unread or unowned status
- a zero or empty count
- an empty progress value
- an empty leaderboard or birthday state
- the signed-out version of a control to a signed-in visitor

A section that is only shown when the visitor has matching data (such as a recommendation) SHALL stay hidden until loading finishes, and SHALL stay hidden if there is nothing to show.

#### Scenario: Status control while loading
- **WHEN** a signed-in visitor has read a work and its status has not finished loading
- **THEN** the work's reading-status control shows a loading placeholder, not "Want to read" or any other unread state

#### Scenario: Counts while loading
- **WHEN** a work's community counts have not finished loading
- **THEN** the stats area shows a loading placeholder, not zero counts

#### Scenario: Load failure
- **WHEN** loading a visitor's status or a page's community figures fails
- **THEN** the affected control or section does not present a guessed state or a zero count as real data

### Requirement: Cached pages keep server-rendered SEO metadata
The cached HTML of every cached page SHALL include that page's title, meta description and, where the page has one, its social share image, exactly as a server-rendered page did before this change.

#### Scenario: Crawler fetches a cached detail page
- **WHEN** a crawler or link-preview service requests a cached work, adaptation, short work or works-by-others detail page
- **THEN** the HTML it receives contains that page's own title, description and share image

### Requirement: Query strings do not change cached page content
The cached HTML of a cached page SHALL NOT depend on the request's query string, so every query-string variant of a page is served the same cached copy. Behavior that relies on a query string on a cached page, such as the sign-in prompt opened by `?signin=1` on the homepage, SHALL be handled in the visitor's browser.

#### Scenario: Homepage with a sign-in prompt query
- **WHEN** a signed-out visitor is sent to `/?signin=1&next=/profile`
- **THEN** they are served the cached homepage, the sign-in prompt opens, and after signing in they are returned to `/profile`

### Requirement: Onboarding still applies on cached pages
The system SHALL still send a signed-in visitor who has not completed onboarding to the onboarding page when they open a cached page. That redirect SHALL happen in the visitor's browser and SHALL never be stored in the shared cache.

#### Scenario: Visitor without a username opens a cached page
- **WHEN** a signed-in visitor who has not chosen a username opens a cached work page
- **THEN** they are sent to the onboarding page

#### Scenario: Other visitors are unaffected
- **WHEN** a visitor who has not completed onboarding opens a cached page, and afterwards a different visitor opens the same page
- **THEN** the second visitor is served the page itself, not a redirect to onboarding

### Requirement: Pages outside the shared cache keep their rendering
The system SHALL NOT serve signed-in-only pages or public profile pages (`/profile/[username]` and its sub-pages) from the shared cache. Public profile pages SHALL continue to be rendered per request with their profile-specific title and description.

#### Scenario: Shared public profile link
- **WHEN** a link-preview service requests `/profile/<username>`
- **THEN** it receives HTML rendered for that request, with that profile's title and description
